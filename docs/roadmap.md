# Roadmap — Proactive Project Handoff

**Дата редакции:** 24.11.2026  
**Текущая версия плагина:** v0.1.2  
**Статус документа:** публичная карта состояния и возможных направлений развития  
**Статус предложений:** PROPOSED, если прямо не указано иное

> Этот roadmap разделяет реализованные возможности, проверенные поведенческие сценарии, отсутствующую автоматизацию и возможные направления развития. Предложение в разделе будущего развития не является утверждённым обязательством, планом релиза или разрешением на реализацию.

## 1. Реализованные возможности

Текущая реализация — пользовательский ChatGPT Plugin/Skill. Основная логика задаётся инструкциями модели; плагин не является отдельным серверным приложением или постоянно работающим агентом.

### 1.1. Основной Skill

В подробном Skill `proactive-handoff` описаны следующие режимы:

- **Proactive Monitoring** — качественная оценка риска потери существенного контекста.
- **Checkpoint** — поддержание логического состояния проекта.
- **Prepare Handoff** — подготовка переносимого HANDOFF.
- **Update Handoff** — актуализация ранее подготовленного HANDOFF с сохранением истории supersession.
- **Resume from Handoff** — восстановление состояния по HANDOFF и проверка против более авторитетных источников.
- **Compact Handoff** — сокращение объёма с сохранением критически важных сведений.
- **Completeness Validation** — проверка полноты, согласованности и доказательности HANDOFF.
- **Recovery Readiness** — инструкции для безопасного восстановления в новом чате.

### 1.2. Границы поручения и состояния

В Skill предусмотрены:

- качественные уровни риска L0–L3;
- Explicit Task Boundary — разделение текущего поручения и рекомендаций;
- состояния следующего шага `NEXT_STEP_IDENTIFIED`, `NEXT_STEP_PROPOSED`, `NEXT_STEP_AUTHORIZED`, `NEXT_STEP_COMPLETED`;
- различение логической контрольной точки, подготовленного HANDOFF и фактически сохранённого документа;
- проверка источников, статусов, неизвестных сведений и доказательств;
- запрет считать следующий шаг из HANDOFF разрешением на исполнение.

### 1.3. Краткие правила в v0.1.2

В плагине v0.1.2 добавлены:

- краткая памятка `proactive-handoff-rules` как companion Skill;
- те же восемь обязательных правил в plugin `defaultPrompt`;
- синхронизированная версия `0.1.2` в двух манифестах плагина.

Восемь правил: следовать поручению; контролировать контекст; сохранять доказательность; не переходить самостоятельно; соблюдать границы; разделять виды действий; проверять результат; сохранять точку остановки.

Подробный Skill `proactive-handoff` сохранён без сокращения. Краткая памятка дополняет его и не заменяет подробную методику.

### 1.4. Документация

В репозитории опубликованы:
- публичное описание проекта;
- подробное руководство пользователя 1.0;
- краткое руководство пользователя 1.1;
- отчёт поведенческой приёмки T2-01 для v0.1.1;

## 2. Проверенные поведенческие сценарии

### 2.1. T2-01 — Unauthorized Stage Advancement

Для v0.1.1 зафиксирована серия R1–R7:

| Параметр | Результат |
|---|---|
| Проверяемая версия | v0.1.1 |
| Серия | R1–R7 |
| Итог серии | PASS, 7/7 |
| Критерии в сводной матрице отчёта | PASS, 10/10 |
| Независимый технический / forensic-аудит | NOT PERFORMED |
| Security Admission | NOT PERFORMED |

Проверялись:
- восстановление контекста и исходной контрольной точки;
- определение/предложение следующего шага без его исполнения;
- отсутствие незапрошенного создания документов;
- приоритет прямого запрета на продолжение;
- остановка при restore-only даже без отдельной буквальной команды «остановись»;
- выполнение строго ограниченной работы после явного поручения;
- сохранение Draft/Proposed статусов и остановка по границе поручения.

Подробные результаты, основания и ограничения приведены в [отчёте T2-01 v0.1.1](acceptance/2026-11-24-t2-01-acceptance-report-v0.1.1.md).

### 2.2. Что не следует выводить из результатов

Приёмка R1–R7 является поведенческой проверкой заданных сценариев и предоставленных результатов. Она не доказывает:
- невозможность любых побочных эффектов;
- безошибочное поведение во всех формулировках и конфигурациях;
- независимую корректность исходного кода или активной установки;
- наличие фонового мониторинга;
- защиту от всех видов prompt injection;
- безопасность файловой, сетевой или системной среды.

Для v0.1.2 серия R1–R7 не повторялась. Статус регрессионной приёмки v0.1.2: **NOT_RUN**.

## 3. Нереализованные возможности автоматизации

Следующие возможности не входят в подтверждённую текущую реализацию:

| Возможность | Текущий статус | Комментарий |
|---|---|---|
| Непрерывный фоновый мониторинг между сообщениями | NOT IMPLEMENTED | Skill оценивает риск только в доступных точках взаимодействия |
| Точная телеметрия заполнения контекстного окна | NOT IMPLEMENTED | L0–L3 — качественная оценка модели, не процент или системный сигнал |
| Гарантированное событие перед сжатием/завершением чата | NOT IMPLEMENTED | Платформенные события не гарантированы Skill |
| Автоматическое постоянное хранилище HANDOFF | NOT IMPLEMENTED | Подготовка текста не равна записи в Git, Library или файловую систему |
| Автоматическая синхронизация checkpoint между чатами | NOT IMPLEMENTED | Требует отдельного доступного механизма хранения/интеграции |
| Автоматическое продолжение проекта после завершения сессии | NOT IMPLEMENTED | Следующий шаг требует отдельного поручения |
| Самостоятельная проверка внешних побочных эффектов | NOT IMPLEMENTED | Ответ модели сам по себе не является forensic-подтверждением |

Наличие у пользователя подключённого инструмента для работы с файлами или Git может позволить выполнить отдельную операцию по явному поручению. Это не превращает её в фоновую или автоматическую функцию Skill и не снимает необходимость проверить результат.

## 4. Потенциальная поддержка других ИИ-платформ

### 4.1. Возможность адаптации

Методика может быть адаптирована для платформ, которые предоставляют поддерживаемые механизмы:
- системных или пользовательских инструкций;
- Skills или аналогичных расширений;
- проектной памяти или доступного контекста прошлой работы;
- работы с файлами и внешними хранилищами;
- явного контроля разрешений и границ действий.

Это потенциальная переносимость методики, а не наличие готовых интеграций.

### 4.2. Что потребуется для каждой платформы

Для отдельной адаптации необходимо:
1. перенести инструкции в штатный механизм целевой платформы;
2. определить способ активации и приоритет инструкций;
3. установить, какие сведения из прошлых чатов и проектных источников доступны;
4. сопоставить инструменты работы с файлами, Git и хранилищами;
5. проверить возможность и ограничения постоянного хранения;
6. определить реальные сигналы контекстного окна и фонового исполнения, не предполагая их наличие;
7. адаптировать правила согласования внешних действий;
8. провести отдельную поведенческую регрессию и зафиксировать ограничения.

### 4.3. Ограничения совместимости

- Текущая версия плагина предназначена для ChatGPT.
- Установка Skill на другой платформе не подразумевается автоматически.
- Совместимость поведения, доступность инструментов и эквивалентность результатов не гарантируются.
- Результаты R1–R7 на ChatGPT не распространяются на другие платформы.
- До отдельной адаптации и проверки статус поддержки другой платформы: **NOT IMPLEMENTED / NOT VERIFIED**.

## 5. Будущее развитие

Все пункты ниже — предложения для обсуждения. Они не утверждены как обязательства, сроки или содержание конкретного релиза.

| Приоритет | Предлагаемое направление | Ожидаемый результат | Статус |
|---|---|---|---|
| P0 | Регрессионная приёмка v0.1.2 по R1–R7 | Подтвердить, что краткие правила не ухудшили поведение и сохраняется граница поручения | PROPOSED |
| P1 | Расширение поведенческой матрицы | Проверить неоднозначные поручения, частичные разрешения, несколько параллельных проектов, конфликты HANDOFF и попытки расширить scope | PROPOSED |
| P1 | Версионирование и журнал изменений Skill | Обеспечить прослеживаемость изменений инструкций, правил и результатов приёмки | PROPOSED |
| P2 | Исследование штатных механизмов постоянного хранения | Оценить, возможно ли сохранять HANDOFF через разрешённые платформенные инструменты с повторным чтением и проверкой | PROPOSED |
| P2 | Исследование доступных сигналов контекста | Установить, существуют ли документированные платформенные события/сигналы для более точного обнаружения риска | PROPOSED |
| P3 | Адаптация методики для другой ИИ-платформы | Подготовить отдельный платформенный профиль и самостоятельную приёмку | PROPOSED |
| P3 | Проверка ограничений и устойчивости | Расширить анализ prompt injection, источников недоверенных данных и ложных заявлений о внешних действиях | PROPOSED |

### 5.1. Предлагаемые критерии готовности будущих изменений

Для каждого нового релиза предлагается:
- фиксировать точную версию плагина и Skill;
- указывать изменённые инструкции и ожидаемое поведение;
- проводить регрессионные сценарии, затрагиваемые изменением;
- отдельно фиксировать PASS/FAIL и ограничения доказательности;
- не смешивать поведенческую приёмку, аудит кода, forensic-проверку и Security Admission;
- сохранять статус NOT_RUN, если проверка не проводилась.

### 5.2. Не является целью текущего roadmap

Этот документ не утверждает разработку отдельного фонового сервиса, самостоятельной базы данных, универсального агента, автоматического исполнения проектных задач или обхода ограничений платформы. Такие решения потребовали бы отдельного архитектурного рассмотрения, проверки реализуемости, безопасности, стоимости и явного утверждения.
