# Руководство пользователя — Proactive Project Handoff

**Версия документа:** 1.0  
**Дата:** 24.11.2026  
**Применимая версия Skill:** v0.1.1 (поведенческая приёмка T2-01, R1–R7: PASS)  
**Назначение:** практическое руководство по использованию Proactive Project Handoff в длительной проектной работе.

---

## 1. Что делает плагин

Proactive Project Handoff — это Skill, который помогает сохранять непрерывность длительной работы с проектом между сообщениями и чатами.

Он помогает:

- замечать моменты, когда важный контекст становится сложным или объёмным;
- поддерживать компактную логическую контрольную точку (checkpoint);
- сохранять решения, ограничения, статусы, риски и доказательства;
- готовить переносимый документ HANDOFF;
- восстанавливать состояние проекта в новом чате;
- отличать следующий рекомендуемый шаг от разрешения его выполнять;
- не выдавать подготовленный документ за сохранённый файл, если фактической записи не было.

**Главный принцип:** автоматизировать сохранение состояния, а не принятие решений и не выполнение следующего этапа за пользователя.

Плагин не является системой управления проектами, автономной базой данных или фоновым агентом. Он задаёт модели методику поведения в рамках доступного контекста и подключённых инструментов.

## 2. Где работает плагин

### 2.1. Текущая реализация

Опубликованный Proactive Project Handoff реализован как Skill для ChatGPT. Его штатное использование предполагает среду ChatGPT, в которой этот Skill установлен и доступен модели.

Это не универсальное расширение, которое можно один раз установить в любой ИИ-сервис.

### 2.2. Можно ли использовать в других ИИ

**Методику — да. Текущую интеграцию — не автоматически.**

Инструкции Skill можно адаптировать для других платформ, например для систем с поддержкой пользовательских системных инструкций, Skills, агентов или проектной памяти. Для этого потребуется:

1. перенести текст инструкции в поддерживаемый целевой платформой механизм;
2. адаптировать способ активации;
3. проверить, какие источники контекста доступны модели;
4. адаптировать работу с файлами, Git и другими хранилищами;
5. отдельно проверить ограничения фоновой работы и автоматического сохранения;
6. провести собственные тесты восстановления и соблюдения границ поручения.

При таком переносе это будет **адаптация методики**, а не автоматически та же самая версия плагина. Совместимость, эквивалентность поведения и результаты тестов ChatGPT на другой платформе не гарантируются.

| Возможность | ChatGPT с активным Skill | Другая ИИ-платформа |
|---|---|---|
| Инструкции проактивного контроля | Да | После адаптации |
| Логические checkpoints в диалоге | Да | Зависит от платформы |
| Подготовка HANDOFF | Да | После адаптации |
| Восстановление из переданного HANDOFF | Да | После адаптации |
| Приоритет явного поручения пользователя | Предусмотрен Skill | Нужно отдельно реализовать и протестировать |
| Доступ к Git/файлам | Только при наличии подключённых инструментов и разрешений | Зависит от интеграций |
| Фоновый мониторинг | Не гарантируется | Не гарантируется |
| Точное определение остатка контекстного окна | Не предоставляется Skill | Зависит от платформы; не следует предполагать наличие |
| Автоматическое постоянное хранение | Не обеспечивается самим Skill | Требует отдельного хранилища или механизма платформы |

## 3. Как начать работу

1. Установите или подключите Proactive Project Handoff в поддерживаемой среде ChatGPT.
2. Убедитесь, что Skill доступен в текущем чате и активирован способом, предусмотренным интерфейсом ChatGPT.
3. Откройте чат проекта.
4. Передайте краткое описание цели, текущего состояния и ограничений либо попросите восстановить состояние из существующего HANDOFF.
5. Дайте стартовое поручение.

Рекомендуемый стартовый запрос:

> Используй Proactive Project Handoff для этого проекта. Веди проактивный контроль контекста, фиксируй значимые решения, ограничения, статусы, риски и точку продолжения. После существенных изменений обновляй логическую контрольную точку. При высоком риске подготовь HANDOFF. Не изменяй файлы, настройки и внешние системы и не запускай код без моего отдельного разрешения. Следующий шаг из HANDOFF не считай разрешением на его выполнение.

Если Skill недоступен или не активирован, один текстовый запрос сам по себе не доказывает, что установленный Skill действительно работает.

## 4. Команды и готовые запросы

У плагина нет обязательного набора специальных slash-команд вида `/checkpoint` или `/handoff`. Ниже приведены обычные текстовые запросы, которые можно отправлять модели. Формулировки можно менять, сохраняя смысл.

### 4.1. Включить проактивное сопровождение

> Веди проактивный контроль контекста этого проекта. После значимых решений и завершения этапов актуализируй логическую контрольную точку. При высоком риске потери контекста подготовь HANDOFF. Не начинай следующий этап без моего отдельного поручения.

### 4.2. Обновить контрольную точку

> Обнови checkpoint проекта по текущему состоянию. Отрази новые решения, выполненную работу, доказательства, ограничения, открытые вопросы, риски и точную точку остановки. Не выполняй следующий этап.

### 4.3. Подготовить HANDOFF

> Подготовь полный HANDOFF для переноса проекта в новый чат. Сохрани утверждённые решения, ограничения, статусы, выполненную работу, источники истины, неизвестные сведения, блокеры и точную точку продолжения. Следующие шаги перечисли как план, а не как разрешение на выполнение. Укажи, был ли документ фактически сохранён во внешнее хранилище.

### 4.4. Обновить ранее подготовленный HANDOFF

> Актуализируй предыдущий HANDOFF с учётом текущего состояния. Сохрани действующие решения и ограничения, отметь устаревшие сведения как SUPERSEDED, не меняй историю задним числом. Выдай полную актуальную редакцию и краткий список изменений.

### 4.5. Проверить полноту HANDOFF

> Проведи Completeness Validation последнего HANDOFF. Проверь полноту решений, ограничений, статусов, доказательств, неизвестных данных, зависимостей и точки остановки. Найди противоречия и неподтверждённые утверждения. Не исправляй документы и не переходи к следующему этапу.

### 4.6. Сократить HANDOFF

> Подготовь Compact Handoff. Сократи повторы и второстепенную историю, но сохрани все утверждённые решения, точные идентификаторы, ограничения, доказательства, риски, блокеры и точку продолжения. Не превращай неизвестное в предположение.

### 4.7. Восстановить контекст в новом чате — только чтение

> Восстанови контекст проекта по переданному HANDOFF. Подтверди цель, решения, ограничения, выполненную работу, текущие статусы, неизвестные сведения и точную точку остановки. Покажи ближайший следующий шаг, но не начинай его, не создавай новые проектные материалы и не меняй checkpoint. После отчёта остановись и ожидай моего поручения.

### 4.8. Разрешить конкретный следующий этап

> Разрешаю выполнить только следующий этап: [название и границы работы]. Сначала перечисли ожидаемые результаты и действия. Не выходи за указанный scope. Не изменяй файлы, не запускай код и не обращайся к внешним системам, если это отдельно не разрешено. После завершения покажи результат и остановись.

Последний запрос следует конкретизировать: например, разрешить только подготовку проекта спецификации в сообщении, но не запись файла и не реализацию.

### 4.9. Зафиксировать остановку

> Зафиксируй текущее состояние проекта и точку остановки. Перечисли выполненное, незавершённое, блокеры и следующий рекомендуемый шаг. Ничего больше не выполняй.

## 5. Уровни риска контекста

Skill использует качественную шкалу риска, а не измеритель заполнения окна.

| Уровень | Значение | Ожидаемое поведение |
|---|---|---|
| L0 — NORMAL | Риск низкий | Продолжать работу; отдельное уведомление обычно не требуется |
| L1 — CHECKPOINT REQUIRED | Нужно зафиксировать новые значимые сведения | Обновить логическую контрольную точку |
| L2 — HIGH RISK | Контекст стал сложным, объёмным или содержит много зависимостей | Подготовить HANDOFF или предложить его как ближайший результат; при достаточном контексте предпочтительно подготовить |
| L3 — CRITICAL | Перенос/завершение чата или высокая вероятность потери важных сведений | Подготовить HANDOFF в текущем взаимодействии, если Skill активен и данные доступны |

Уровни L0–L3 — качественная оценка модели. Они не означают, что ChatGPT передал плагину точный процент заполнения контекстного окна или системное событие о его скором исчерпании.

## 6. Что должно быть в хорошем HANDOFF

В зависимости от проекта документ должен содержать:

- название и цель проекта;
- критерии готовности;
- источники истины и ссылки на документы;
- утверждённые, отклонённые и предварительные решения с их статусами;
- обязательные ограничения и запреты;
- текущее состояние и доказательства выполненной работы;
- архитектуру и технические контракты;
- открытые вопросы, риски и блокеры;
- неизвестные и непроверенные сведения;
- точную точку остановки;
- следующий шаг и его зависимости;
- прямую инструкцию следующему чату.

Следующий шаг — это описание точки продолжения, а не разрешение начать работу.

## 7. Важнейшие ограничения и безопасность

### 7.1. Контекст и фоновая работа

Skill не является системным обработчиком жизненного цикла ChatGPT. Он:

- не получает гарантированно точный процент заполнения контекстного окна;
- не получает гарантированно событие сжатия контекста или завершения чата;
- не работает гарантированно в фоне между сообщениями;
- не гарантирует запуск непосредственно перед исчерпанием контекста;
- не продолжает работу после завершения сессии самостоятельно.

Проактивность означает оценку риска в моменты доступного взаимодействия, а не непрерывный скрытый мониторинг.

### 7.2. Хранение и перенос

Логическая контрольная точка в сообщении не равна файлу или постоянной базе данных.

Подготовленный в ответе HANDOFF не означает, что он автоматически сохранён в Library, GitHub или локальной файловой системе. Для постоянного хранения необходим реально доступный инструмент и отдельное подтверждение результата записи.

Различайте состояния:

- `HANDOFF_DRAFT_PREPARED` — текст подготовлен;
- `HANDOFF_PERSISTED` — запись во внешнее хранилище подтверждена;
- `HANDOFF_VERIFIED` — сохранённый документ повторно прочитан и проверен.

Не считайте эти статусы взаимозаменяемыми.

### 7.3. Пользовательское разрешение и границы поручения

Наличие следующего шага в HANDOFF, checkpoint или рекомендациях не означает разрешения его выполнять.

Без явного поручения нельзя:
- начинать следующий этап;
- создавать незапрошенные проектные документы;
- расширять scope;
- менять контрольную точку на основании незапрошенной работы;
- изменять внешние файлы, настройки, базы данных или репозитории;
- устанавливать компоненты;
- запускать код или тесты;
- выполнять публикацию или другие внешние действия.

Разрешение на один вид действия не распространяется автоматически на другой. Например, разрешение подготовить спецификацию не разрешает записать её в Git или начать реализацию.

### 7.4. Защита информации

Не включайте в HANDOFF:
- пароли, API-ключи, токены и приватные ключи;
- секреты и данные аутентификации;
- персональные идентификаторы и чувствительные сведения, не необходимые для продолжения;
- приватные материалы, предназначенные только для внутреннего использования, в публичный репозиторий.

Для публичного GitHub-репозитория создавайте отдельную очищенную редакцию. Перед публикацией проверьте её на секреты, персональные данные, внутренние пути, адреса и конфиденциальные детали.

### 7.5. Источники и достоверность

Плагин не должен:
- выдумывать отсутствующие решения или структуру данных;
- выдавать предположения за факты;
- считать Draft утверждённым;
- заявлять об успешной записи или тестировании без результата;
- считать старый HANDOFF более авторитетным, чем актуальный источник истины;
- повторять уже завершённую диагностику без причины.

## 8. Рекомендуемый рабочий цикл

1. **Начало проекта:** активировать Skill и передать исходные документы, цель и ограничения.
2. **В ходе работы:** поручать значимые задачи обычным языком; модель фиксирует решения и состояние.
3. **После существенного изменения:** обновить checkpoint.
4. **Перед крупным переходом:** оценить риск и полноту текущего состояния.
5. **При высоком риске или переносе:** подготовить HANDOFF.
6. **В новом чате:** передать HANDOFF и запросить restore-only.
7. **После восстановления:** проверить точку остановки и только затем отдельно поручить следующий этап.
8. **При необходимости постоянного хранения:** сохранить документ в согласованном хранилище и проверить его повторным чтением.
